# Wikidot API Reference

XML-RPC APIの運用レファレンス。本書は公式ドキュメントの再整理版で、Python 3用にコード例を統一してある。メソッドシグネチャ・型・エラー種別は概ね古いまま有効で、変わったのは接続と認証の書き方だけである（§2参照）。

> このリポジトリでは、個別slugの取得には`scripts/fetch_wikidot.py`、サイト全体のバルク同期には`scripts/corpus_sync.py`を使う。両方とも内部では`scp_wiki_wikidot/`パッケージを介してWikidotと通信する（`CLAUDE.md`参照）。
>
> ライブラリ層として呼び出したい新しいスクリプトを書く場合は`scp_wiki_wikidot/`パッケージを使う。認証ヘッダ、レート制御、再試行、状態機械はすべて`scp_wiki_wikidot.transport.Transport`が引き受け、型付きメソッドは`scp_wiki_wikidot.client.WikidotClient`から生える。サイト側でXML-RPC APIが無効な場合、`pages.*` / `users.get_me` / `posts.*`は同じclient面のまま`wikidot.py`へフォールバックする。`files.*`はXML-RPC呼び出しのみでフォールバックしない。設計の全体像は[`docs/corpus-sync.md`](../docs/corpus-sync.md) §9.1にある。

> 現行のcorpus同期は添付ファイルの内容を保存しない。以下の`files.*`仕様はAPIリファレンス、clientの直接利用、過去runの対象slot復旧のために残している。新しいcorpus captureでは`files.select`、`files.get_meta`、`files.get_one`、`files.download`を呼び出さない。

サイト全体のread resourceと未知fieldを漏れなく保存する監査可能なprofileは、
`scripts/corpus_sync.py --capture-profile xmlrpc-complete --transport xmlrpc`
で実行する。`--limit` / `--slug`はこのprofileでは使用できない。保存形式、削除追従、
完了gate、offline verifierは[`docs/corpus-sync-xmlrpc-complete-capture-design.md`](../docs/corpus-sync-xmlrpc-complete-capture-design.md)を正本とする。

## 1. 概要

Wikidot APIは外部プログラムからユーザの代理としてWikidotと対話するためのXML-RPCサービスである。認証には個別に発行されるAPIキーを用いる。

- エンドポイント: `https://www.wikidot.com/xml-rpc-api.php`
- プロトコル: XML-RPC over HTTPS（SSL必須）
- 認証: HTTP Basic Authentication
  - Username: 呼び出し側アプリケーション名（任意、例: `scp-wiki-translation`）
  - Password: ユーザのAPIキー
- レート制限: 240 requests / minute / user

実運用では、2026-08-07に複数のcorpus captureを同時実行した際、HTTP 429が返り、本文は
`XML-RPC request limits: http://www.wikidot.com/doc:api`、headerには`Retry-After: 30`
が含まれていた。これはページmethodの実装ミスではなく、ユーザー単位の共有制限に到達した
サーバー応答である。レスポンス本文・header・retry待機はrunのerror-response artifactへ
保存する。複数プロセスを動かすときは各プロセスの
`SCP_WIKIDOT_XMLRPC_REQUEST_RATE`を下げ、合算で制限を超えないようにする。

APIキーは**ユーザアカウントに紐づく**ものであり、Wikiごとに個別のAPIキーが存在するわけではない。Wiki側で設定できるのは *Manage Site* » *API* における API access の許可（read / write）のみである。したがって「このサイトのAPIキーが設定されていない」という表現は誤りで、正しくは「このサイトでAPI accessが許可されていない」もしくは「APIキーを持つユーザーが存在しない」となる。

APIキーの取得場所: *My Account* » *Settings* » *API access*。キーはパスワード同等に扱い、漏洩した疑いがあれば即座に再生成する。

このリポジトリでは以下の環境変数を使う：

| 変数 | 用途 |
|---|---|
| `WIKIDOT_APP_NAME` | Basic認証のユーザ名（アプリ名） |
| `WIKIDOT_API_KEY` | Basic認証のパスワード（秘匿） |
| `WIKIDOT_USERNAME` | `wikidot.py`フォールバックでログインが必要な操作を行う時のWikidotユーザ名 |
| `WIKIDOT_PASSWORD` | `wikidot.py`フォールバックでログインが必要な操作を行う時のWikidotパスワード |
| `SCP_WIKIDOT_XMLRPC_REQUEST_RATE` | corpus captureの1プロセスあたりの平均XML-RPCリクエスト数（既定値`4.0`） |

## 2. 接続の雛形（Python 3）

### 2.1推奨: `scp_wiki_wikidot/`パッケージ経由（新規コード向け）

```python
from scp_wiki_wikidot.client import WikidotClient
from scp_wiki_wikidot.config import get_credentials
from scp_wiki_wikidot.transport import Transport, build_server_proxy

app_name, api_key = get_credentials()         # env vars を raise-on-missing で取得
proxy = build_server_proxy(app_name, api_key) # Authorization ヘッダ版 ServerProxy
transport = Transport(proxy)                  # token bucket + state machine + retry
client = WikidotClient(transport, site="scp-wiki")

# 型付きメソッド
page = client.pages_get_one("scp-173")
metas = client.pages_get_meta(["scp-173", "scp-500"])  # 最大 10 件

# 生 XML-RPC が欲しい場合
raw = client.pages_get_one_raw("scp-173")
```

この経路ではAPIキーがURLに埋め込まれない（Authorizationヘッダ経由）。`ServerProxy.__repr__`や`xmlrpc.client.ProtocolError.url`にAPIキーが漏れない、という不変条件を守りたい場合はこれを使う。`WikidotClient`は、Wikidot側が「Access to this site through the API is forbidden」を返した場合だけ`scp_wiki_wikidot.wikidot_py.WikidotPyFallbackClient`へ委譲する。ページ列挙、メタ取得、本文取得、保存、`users.get_me`相当、投稿列挙、投稿取得のclient面は同じまま使える。

### 2.2低レイヤ直叩き（レガシー、参考用）

URLに認証情報を入れる旧形式。新規コードでは使わないこと。`scripts/check_wikidot_access.py`が既存互換のためにまだ使っている以外、リポジトリ内でこの書き方を採用している箇所は無い。

```python
import os
from xmlrpc.client import ServerProxy, Fault

app_name = os.environ["WIKIDOT_APP_NAME"]
api_key = os.environ["WIKIDOT_API_KEY"]

# Deprecated: 認証情報が URL に入るため repr やエラーで漏れる恐れがある
server_url = f"https://{app_name}:{api_key}@www.wikidot.com/xml-rpc-api.php"
s = ServerProxy(server_url)

# 利用可能なメソッド一覧
print(s.system.listMethods())
```

返るメソッド一覧（2025時点）:

```
['system.listMethods', 'system.methodHelp', 'system.methodSignature', 'system.multicall',
 'categories.select', 'tags.select',
 'pages.select', 'pages.get_meta', 'pages.get_one', 'pages.save_one',
 'files.select', 'files.get_meta', 'files.get_one', 'files.save_one',
 'users.get_me', 'posts.select', 'posts.get']
```

### `system.methodSignature`について

サーバ側は`system.methodSignature`を受け付けるが、戻り値は`[{'returnType': 'void', 'parameters': ['struct']}]`のように極めて大雑把で、引数の個別フィールドや戻り値の具体的な型は判らない。型を知りたければ実測するしかない。本書の型注釈は実測に基づく。

### 命名規則

| パターン | 意味 |
|---|---|
| `<namespace>.select` | 識別子（名前やID）のリストを返す |
| `<namespace>.get` | 複数オブジェクトの詳細をdictのリスト／dictで返す |
| `<namespace>.get_one` | 単一オブジェクトの詳細dictを返す |
| `<namespace>.get_meta` | メタデータのみを一括取得（本文を含まない） |
| `<namespace>.save_one` | 単一オブジェクトの作成・更新 |

### エラー処理

XML-RPCのエラーは`xmlrpc.client.Fault`として送出される。`scp_wiki_wikidot/`パッケージ経由なら`WikidotFault` / `WikidotProtocolError`にラップされており、トランスポート層のエラーとアプリケーション側のエラーを区別できる：

```python
from scp_wiki_wikidot.errors import WikidotFault, WikidotProtocolError

try:
    page = client.pages_get_one("scp-173")
except WikidotFault as e:
    # 到達はできたが、サーバが「存在しない」「権限がない」等を返した
    print(f"API fault {e.fault_code}: {e.fault_string}", file=sys.stderr)
    sys.exit(1)
except WikidotProtocolError as e:
    # HTTP レイヤの失敗（URL はトークン抜きに redact 済み）
    print(f"Protocol error {e.errcode}: {e.errmsg}", file=sys.stderr)
    sys.exit(1)
```

低レイヤ直叩き（§2.2）経由の場合の等価形：

```python
try:
    result = s.pages.get_one({"site": site, "page": page})
except Fault as e:
    print(f"API fault: {e.faultString}", file=sys.stderr)
    sys.exit(1)
except Exception as e:
    print(f"Connection error: {e}", file=sys.stderr)
    sys.exit(1)
```

## 3. メソッド一覧

### `categories.select`

サイト内の全カテゴリ名を返す。

- 引数
  - `site` (string, required)
- 戻り値: `list[str]` — カテゴリ名
- 例
  ```python
  >>> s.categories.select({"site": "my-site"})
  ["_default", "admin", "forum", "system", "blog"]
  ```

---

### `tags.select`

指定条件に合致するページに付与されたタグの一意なリストを返す。

- 引数
  - `site` (string, required)
  - `categories` (list[str], optional) — カテゴリで絞り込み
  - `pages` (list[str], optional) — 対象ページのフルネーム。最大10件
- 戻り値: `list[str]`

---

### `pages.select`

条件に合致するページのフルネーム一覧を返す。パラメータは概ね[ListPagesモジュール](https://www.wikidot.com/doc:listpages-module)のオプションに準拠する。

- 引数
  - `site` (string, required)
  - `pagetype` (string, optional, default `"*"`)
  - `categories` (list[str], optional)
  - `tags_any` (list[str], optional) — いずれか1つ以上を持つ
  - `tags_all` (list[str], optional) — 全てを持つ
  - `tags_none` (list[str], optional) — いずれも持たない
  - `parent` (string, optional) — フルネーム、または`"-"`で親なし
  - `created_by` (string, optional)
  - `rating` (string, optional) — 例: `">0"`, `"<0"`
  - `order` (string, optional) — 例: `"created_at desc"`
- 戻り値: `list[str]`
- 例
  ```python
  >>> s.pages.select({
  ...     "site": "my-site",
  ...     "categories": ["blog", "news"],
  ...     "tags_none": ["_draft"],
  ...     "order": "created_at desc",
  ... })
  ["blog:last-post", "blog:second-post", "blog:first-post", "blog:_template"]
  ```

`fetch_wikidot.py`では子ページの列挙に`{"site": site, "parent": parent_fullname}`の形で使っている。

  - `pages` (list[str], required) — 最大10件
- 戻り値: `dict[str, dict]` — キーはフルネーム。各値の中身：

実測上、指定したページが1件も存在しない場合は空のlist `[]` が返ることがある。client層ではこれを空dictとして正規化する。存在しないページを成功と判定せず、必要なら個別取得とdeferred/fault処理へ渡す。

### `pages.get_one`

単一ページの詳細（本文・HTML含む）を取得する。`fetch_wikidot.py`の中核では、`scp_wiki_wikidot.client.WikidotClient.pages_get_one_raw`でAPI形状のdictを受け取る。型付きにしたい場合は`pages_get_one`を使う（戻り値は`scp_wiki_wikidot.models.Page` dataclass）。

- 引数
  - `site` (string, required)
  - `page` (string, required) — フルネーム（例: `"scp-173"`, `"blog:first-post"`）
- 戻り値: `pages.get_meta`の全フィールドに加えて：

  | フィールド | 型 | 説明 |
  |---|---|---|
  | `parent_title` | str \| None | 親ページタイトル |
  | `children` | int | 子ページ数 |
  | `content` | str | ページのソース（Wikidotマークアップ）。data formを使うページではYAMLの場合あり |
  | `html` | str | レンダリング済みHTML |
  | `comments` | int | コメント数 |
  | `commented_at` | str \| None | 最終コメント日時 |
  | `commented_by` | str \| None | 最終コメント投稿者 |

#### `html`と通常GETの差異

`html`は通常のページGETで返るHTML文書や、その文書にある`#page-content`の内側と同一ではない。

XML-RPCはページ本文の静的なレンダリング済みHTML断片を返すが、閲覧時に評価されるモジュールやブラウザ用のイベント属性を完全には含めない。

2026年7月12日に`scp-wiki`の`svg-animation`、`scp-173`、`foundation-missed-connections`で実測したところ、3ページとも`pages.get_one().html`と通常GETの`#page-content`は、生バイト、DOM要素数、可視テキストのいずれも一致しなかった。

確認できた差異は次のとおりである。

- `[[module Rate]]`はXML-RPCでは空になり、通常GETでは現在のratingと投票ボタンに展開される。
- `[[module ListPages]]`の結果はXML-RPCでは空になり、通常GETでは問い合わせ結果に展開される。
- `[[module CSS]]`の生成CSSはXML-RPCのHTML断片から省かれ、通常GETでは`<head>`内の`<style>`に配置される。
- XML-RPCではfootnoteなどの`onclick`属性が省かれるが、通常GETにはWikidotのイベントハンドラが入る。
- HTMLエンティティ、空白、属性の引用符にもシリアライズ差がある。
- 通常GETにはサイトのヘッダー、サイドバー、フッター、ページ操作UI、スクリプトが含まれるが、XML-RPCの`html`には含まれない。

一方、include、条件分岐、テーブル、段落など、動的モジュールに依存しない静的構文の調査には`html`を利用できる。

たとえば`svg-animation`では、引用内にある12個の`> [[include :scp-wiki:svg-animation ...]]`が、XML-RPCと通常GETの両方で展開されず可視テキストとして残った。

この結果は、XML-RPCの`html`が静的include構文の比較には使える一方、RateやListPagesを含む最終ページDOMの正本にはならないことを示す。

2026年7月13日に`scp-wiki:theme:yossistyle`で追加確認したところ、sourceには`[[module CSS]]`が1個あったが、XML-RPCの`html`には`<style>`がなく、通常GETには`</head>`より前の`<style>`内にCSSモジュール固有の規則があった。ブラウザ用HTMLではCSSモジュールをdocument headへ注入し、XML-RPC互換の本文HTML断片には再結合しないのが実挙動に一致する。

取得手段は検証対象に応じて使い分ける。

1. 静的なWikidot構文の一次比較には`pages.get_one().html`を使う。
2. Rate、ListPages、Backlinks、CountPages、閲覧者状態、権限、イベント属性の比較には通常GETから`#page-content`を抽出して使う。
3. JavaScript実行後のDOM、操作、CSSレイアウト、ネットワーク挙動には実ブラウザを使う。
4. 最終的な互換性判定では、XML-RPCの`html`だけを合格根拠にしない。

`WikidotClient`がサイトのAPI禁止を検出して`wikidot.py`へフォールバックした場合、現在のフォールバック実装は`html`に空文字列を返す。

2026年8月7日の実測では、`scp-vn` は`users.get_me`だけが成功し、`pages.get_one`、`pages.get_meta`、`pages.select`はすべて403の`Access to this site through the API is forbidden (configure in "Manage Site > API")`を返した。`WikidotPyFallbackClient(site="scp-vn")`では同じページの本文・タイトル・親・タグを取得できたため、`scp-vn`のページメタデータ取得はXML-RPC clientのfallbackを有効にした経路で行う。これは公開先`scpaiueouiuiuiui`の作成可否や認証主体の証拠ではない。

フォールバックの可能性がある処理では、`html`が空なら通常GETまたはブラウザ取得へ切り替える必要がある。

同じ実測では、XML-RPCの取得時間は1ページあたり0.199秒から0.708秒、通常GETは0.706秒から1.105秒だった。

ただし、XML-RPCには1ユーザーあたり毎分240リクエストの制限があるため、この小規模な測定値だけでサイト全体のバルク取得が常に速いとは判断できない。

sourceやmetadataの同期ですでに`pages.get_one`を呼ぶ処理は、同じ応答の`html`を静的構文の検査に再利用できる。最終的な`#page-content`が必要な処理はXML-RPCを前置せず通常GETへ直接進む。大量監査では取得済み`content`から対象構文を分類し、静的構文だけをXML-RPCで一次判定し、動的モジュールを含むページだけを通常GETまたはブラウザへ送る。

認証cookieを渡さない通常GETは匿名閲覧者として動く。会員状態や非公開ページの権限差を調べる場合は閲覧者identityを揃え、証拠にもroleを記録する。

#### 非公開サイトでの取得と検証

2026年7月13日の実測では、ログイン済みmemberでも`wikidot.py`の高水準`site.page.get()`が先に呼ぶ`ListPagesModule`が非公開サイトでForbiddenになる場合があった。この例外をページ不存在へ読み替えてはいけない。対象slugへの認証済み通常GETから`WIKIREQUEST.info.pageId`と`#page-title`を取得し、そのpage IDを`viewsource/ViewSourceModule`へ渡すと、ListPagesを経由せずsourceを取得できた。不存在と判断できるのは固定した対象originへの認証GET自体がHTTP 404を返した場合だけである。

HTTPだけで運用される検証サイトへ接続する場合も、回避策を任意のWikidot siteへ一般化しない。書き込みを明示許可された単一originへhost、scheme、portを固定し、redirectを拒否し、environment proxyを無効にした専用clientを使う。

新規ページの検証書き込みでは認証GETの404に加え、保存直前にも既存のpage revision IDまたはpage IDがないことを確認する。削除は作成時に記録したpage ID、title、source SHA-256が現在値と一致する場合だけ行う。remote mutation前にrun-owned slug、期待title、source SHA-256を永続ledgerへ記録する。

同日のAMC保存では、末尾LFを1個持つsourceに対して保存後のViewSourceがそのLFだけを除いた本文を返した。受理済みsource hashを保持したまま、AMC保存をViewSourceで検証する処理ではWikidot対象に限って末尾LFを1個除いたremote round-trip hashもmutation前のledgerへ記録する。これをXML-RPC保存や任意の改行正規化へ一般化しない。

`theme:`categoryへの保存後、通常GETの`#page-content`が保存sourceではなくsite側の`theme:_template`に置換される例も確認された。XML-RPCと通常GETを比較する検証ではcategory templateの有無を先に確認し、accepted source固有markerが`#page-content`にあることを必須条件にする。

### `pages.save_one`

ページを作成・更新する。`site`と`page`以外は変更したいキーのみ指定する（省略したキーは既存値が保持される）。

- 引数
  - `site` (string, required)
  - `page` (string, required)
  - `title` (string, optional)
  - `content` (string, optional) — Wikidotソース
  - `tags` (list[str], optional) — 既存タグを置換
  - `parent_fullname` (string, optional) — `"-"`で親を外す
  - `save_mode` (string, optional)
    - `"create"` — 新規作成のみ。既存なら例外
    - `"update"` — 更新のみ。存在しなければ例外
    - `"create_or_update"` (default)
  - `rename_as` (string, optional) — 他の変更と同時にリネーム
  - `revision_comment` (string, optional)
  - `notify_watchers` (bool, optional, default `false`)
- 戻り値: 保存後のページ情報dict（`pages.get_one`と類似の構造）

#### 2026年8月9日の親解除と先頭LF調査

`scpaiueouiuiuiui`の既存ページ更新で、`parent_fullname`を省略すると既存parentが保持され、空文字列を送るとXML-RPCは`WikidotFault`を返した。`parent_fullname: "-"`を送ると既存の`everkeep-hub` parentが解除され、認証再取得でも`parent_fullname`は空になった。親を外す更新では空文字列や省略を使わず、`"-"`を明示する。

#### 2026年8月4日のXML-RPC新規作成調査

2026年8月4日に`scpaiueouiuiuiui`を対象に、認証主体の照合と診断用の限定された新規作成を行った。認証主体と新規作成の証拠を混同しないため、次の事実を記録する。

- XML-RPCの`users.get_me`は、API主体を`rokurokubi`（ID `5700026`）として返した。
- AMCで使う認証済みセッションは、`scpaiueouiuiuiui`（ID `8955132`）としてページHTMLに現れた。
- AMCで作成されたページの観測では、`created_by`は`scpaiueouiuiuiui`であり、XML-RPC主体の`rokurokubi`とは異なる。
- `pages.select(created_by="Rokurokubi")`は`codex-file-smoke-027e3eba`だけを返した。このページの現在の本文は`deleted`である。
- このスモークページを作成した経路は、現在のrun成果物とソースから復元できない。したがって、これを`pages.save_one`の成功対照とは扱わない。
- 既存の新規作成失敗は、運用側の`SanitizedOperationError`によって`WikidotFault`という型だけが保存される。`fault_code`と`fault_string`は保存されない。
- 後続の存在確認で得た`WikidotFault`コード406は、別の読み取り操作の「ページ不存在」エラーである。新規作成時のfault codeとして再利用してはいけない。
- ライブの`system.methodHelp("pages.save_one")`は、本文、タグ、親ページなどの必須項目だけを表示し、`save_mode`や`revision_comment`などの任意項目を表示しなかった。この省略だけでは、任意項目が拒否されるとは判断できない。
- プロジェクトのサニタイズ層を通さない標準ライブラリのXML-RPCコードで、UUID付き診断ページを作成した。`site`、`page`、`title`、`content`だけの作成は成功し、レスポンスに`created_by: "Rokurokubi"`が含まれた。
- 同じ最小リクエストへ`save_mode: "create"`だけを加えた作成も成功した。`revision_comment`だけを加えた作成も成功した。
- 空の`tags: []`と、存在する親ページを指定した作成も成功した。
- 非空の`tags: ["codex-diagnostic"]`を加えたfresh createは、`404 / "Unknown error"`で失敗した。
- 存在する親、非空タグ、`save_mode: "create"`、`revision_comment`を同時に指定した、デプロイと同じ形のfresh createも同じ`404 / "Unknown error"`で失敗した。
- タグなしで作成した診断ページへ、別の`pages.save_one`更新として非空タグと`save_mode: "update"`を送ると成功した。再読込でタグが保存され、`revisions`は`0`から`1`になった。
- 最小本文を末尾LF付きで作成したとき、保存レスポンスと再読込結果から末尾LFが1個除去された。このサイトのXML-RPC保存にも、本文の末尾LF正規化がある。

この調査から、次の範囲までを確定する。

1. AMCの成功履歴は、XML-RPCの新規作成成功の証拠にならない。プロトコルと認証主体が異なるためである。
2. XML-RPC主体がサイト全体で新規作成を拒否されるとはいえない。少なくとも同じ主体名の作成者を持つページが1件ある。ただし、その作成経路は未確定である。
3. 今回のfresh create faultの根本原因は、非空タグをfresh createの同一`pages.save_one`リクエストへ含めていることである。対象サイトはこの組み合わせを`404 / "Unknown error"`として返す。
4. `save_mode`、`revision_comment`、存在する親ページ、空のタグ配列は、今回のfaultの原因ではない。
5. 対象サイトで測定した回避手順は、fresh createから非空タグを外し、作成後の別の更新でタグを保存する方法である。この手順を別サイトへ一般化してはいけない。

デプロイ側のfresh createは、対象サイト向けに非空タグを作成リクエストから分離し、作成後の`save_mode: "update"`でタグを保存する。本文・タイトル・親の一致確認、更新失敗の記録、再実行時のメタデータだけの再開、最終メタデータ検証までを同じ安全ゲートで行う。

#### 2026年8月4日の公開planでの認証済み親ページ確認

`scpaiueouiuiuiui`では、認証済みXML-RPCの`pages.get_one`で存在するページでも、未認証の通常HTTP取得がHTTP 404になることがある。`simple-sketches`とその親`peregrine`でこの組み合わせを再現した。したがって、未認証HTTPの404を非公開ページや親ページの不存在の証拠として使ってはいけない。

公開planの対象サイト内のページ、親、include依存の存在確認は、APIキーで認証した`pages.get_one`を優先する。外部assetの可用性確認は、引き続き宣言された公開HTTPS URLへの読み取り専用HTTP取得で行う。認証済み取得がページ不存在を返す場合だけ、そのページを不存在と判定する。

cross-site includeでは、支部側のAPI設定によって認証済み`pages.get_one`が403（`Access to this site through the API is forbidden`）を返すことがある。2026年8月4日に`snippets:image`でこの状態と、認証不要の固定HTTPS GETがHTTP 200を返す組み合わせを確認した。公開planはこの場合に限り、許可されたinclude siteの固定URLへ読み取り専用GETを行う。対象サイト自身のページや親ページを、未認証GETへフォールバックして存在確認してはいけない。

#### 公開後source検証の端末LF正規化

2026年8月4日の`scpaiueouiuiuiui`更新で、`scp-9167`はcanonical sourceが末尾LFを1個持つのに対し、XML-RPC保存後の認証済み`pages.get_one`はそのLFだけを除いた本文を返した。本文の他のバイトとmetadataは一致し、`scp-9308`と`scp-910`ではsourceもmetadataも完全一致した。

このサイトの公開observeでは、canonical sourceとlive sourceが完全一致する場合を`source_comparison: exact`とし、対象サイトに限ってcanonical末尾LFを1個だけ除いた場合を`source_comparison: wikidot_terminal_lf_stripped`として記録する。その他の差分は失敗であり、任意の改行正規化や別サイトへの一般化は行わない。

#### fullnameの60文字境界

2026年7月13日に`scpaiueouiuiuiui.wikidot.com`の通常GETで実測したところ、64文字のfullnameを指定したURLはHTTP 301で先頭60文字のfullnameへ正規化された。
60文字以下のURLではこの正規化は発生しなかった。

作成前の存在確認、保存、保存後の検証、削除で61文字以上のfullnameを使うと、呼び出し側が意図した名前とWikidotのHTTP正規名がずれる可能性がある。
そのため自動化では保存前にfullnameを60文字以下へ制限し、通常GETがredirectを返した場合は「不存在」とみなさず停止する。

この観測は通常GETに対するものであり、`pages.save_one`が61文字以上のfullnameを拒否するか、切り詰めるかは今回の測定では確認していない。
XML-RPC保存の挙動を通常GETの結果だけから推定しないこと。

### ファイル名とURLのエスケープ境界

XML-RPC APIのファイル引数と、添付ファイルを取得するHTTP URLは別の名前空間である。
ファイル名をURL用にpercent-encodeしてからXML-RPCへ渡してはならない。

- `files.select`の戻り値、`files.get_meta`の`files`引数、`files.get_one`の`file`引数、`files.save_one`の`file`引数は、Wikiに登録されたファイル名そのものをUTF-8文字列で扱う。
  例えばファイル名が`B&W.png`なら、これらの値は`B&W.png`であり、`B%26W.png`ではない。
- XML-RPCのwire上ではXMLの規則に従い`&`が`&amp;`として表現されるが、XML-RPCライブラリが復号したPython側の値は`B&W.png`になる。これはURL percent-encodingではない。
- 添付URLのpathでは、ページfullnameとファイル名がpath segmentとしてpercent-encodeされる。例えば同じ添付は、実siteのページFiles画面から次のように返る。

  ```text
  https://scp-wiki.wikidot.com/local--files/art:i-know-pizza/B%26W.png
  https://scp-wiki.wdfiles.com/local--files/art%3Ai-know-pizza/B%26W.png
  ```

  `:`の扱いがhostによって異なる場合があるが、`B%26W.png`の`%26`はファイル名中の`&`を表す。URLをXML-RPCのファイル名に戻す処理で`urllib.parse.unquote`を使ってはいけない。
- `download_url`はAPIが返したURLをHTTP取得にそのまま使う。URLを組み立てる必要がある場合だけ、ページfullnameとファイル名をそれぞれURL pathとしてencodeする。XML-RPCのstruct keyとURLのbasenameを相互に推測しない。

#### `files.get_meta`のstruct keyに関する実測上の注意

仕様上は戻り値dictのkeyが要求したファイル名になる。しかし、2026-08-06に実`scp-wiki`の`art:i-know-pizza`で、次の不整合を実測した。

- `files.select`は`B&W.png`を含む8件を返した。
- 同じ`B&W.png`を含むbatchを`files.get_meta`へXML-RPCで渡すと、戻り値は`"B&W.png"`をkeyにせず、`""`をkeyにしたentryを返した。
- そのentry内部の`filename`は正しく`B&W.png`で、`size`、`mime_type`、`download_url`などのmetadataも存在した。
- `files.get_one(page="art:i-know-pizza", file="B&W.png")`は、同じ文字どおりのfile引数で成功し、`content`も返した。

したがってconsumerは、まずstruct keyとの完全一致を使い、一致しない場合に限り、entry内の`filename`が要求名と完全一致するentryを一意に探して復元する。URL-decoded名、大小文字違い、部分一致、複数候補の推測で補ってはならない。一意に復元できない場合は、添付の削除とみなさず、`files.get_meta`の生レスポンスを保存したうえで不完全取得として扱う。

この実測はXML-RPC仕様の正常系ではなく、現行Wikidot APIの応答異常である。`wikidot.py`の`Page.files`は`files/PageFilesModule`をAMCで取得し、Files画面のliteralな表示名とpercent-encoded URLを別々に保持するため、この境界の確認に使える。

## 4. 運用上の注意

- レート制限240 req/min/userを意識する。`pages.get_meta` / `files.get_meta` / `posts.get`は1リクエストあたり最大10件なので、バッチ化すれば実質の取得速度はその10倍になる。
- バックオフ: `Fault`で返ってきた場合はリトライする前に原因を確認する。単純な再送ループはレート制限に抵触しやすい。
- 子ページ取得: `pages.select`に`{"parent": "<fullname>"}`を渡すと子ページのフルネーム一覧が得られる。`WikidotClient.pages_select(parent=...)`が型安全なラッパ。
- サイト名 → ブランチコードのマッピングは`scripts/wikidot_paths.py`の`WIKI_TO_BRANCH`が一次情報。新しい支部を扱う前にそちらを更新する（`scp_wiki_wikidot.config` / `scripts/fetch_wikidot.py`は同じテーブルを再エクスポートしている）。
- 公式フォーラム: APIに関する議論はWikidot開発者フォーラムのスレッド`t-257156`にある（URLは変動するので検索推奨）。
