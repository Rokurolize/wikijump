# Candidate artifact binding

Performance evidence is authoritative only when the measured Deepwell executable is bound to a `roku.candidate_build_manifest.v1` manifest. The manifest embeds the complete JSON emitted by `roku-resource-lease artifact-key`, including the repository and FTML source identities, `rustc -Vv` and Cargo identities, linker identity, profile, target, sorted Cargo features, flags, and captured build environment. The Cargo.lock SHA-256 is included as the `cargo-lock` recipe digest. The manifest separately records the executable SHA-256.

Use `../scripts/build-deepwell-candidate.sh` so the build and artifact-key probes share the same environment. It checks the lease registry and legacy processes, uses an isolated target directory and sccache, selects an interactive lease for dev or an exclusive lease for release, records the complete artifact-key payload before and after Cargo, requires those payloads and Cargo.lock to remain identical, and writes the manifest immediately after Cargo succeeds.

The build wrapper and `../scripts/candidate-artifact-manifest.py` are source-owned verification tools. Current candidate and acceptance code must not depend on copies under `/home/roku/wjlab/scripts/`; those paths are historical provenance only.

Pass the manifest to measurement commands with `--candidate-manifest`. Each command hashes the executable and adjacent Cargo.lock inside the runtime container, extracts the exact FTML revision from that lockfile, and verifies all values against the manifest before creating or resuming a database measurement run. The disposable runtime stack additionally requires the manifest's wrapped pre/post build receipt to bind the artifact key, build command, Cargo.lock, and executable independently of caller-supplied labels. A full-inventory resume also requires the same artifact key and manifest digest as the original run.

Acceptance mode fails closed unless the manifest carries the wrapped pre/post build receipt, the manifest is structurally valid, the measured binary and Cargo.lock match, both source identities are clean, the repository and FTML SHAs match, and the profile is release. Direct post-hoc use of `candidate-artifact-manifest.py create` is diagnostic-only because probing a toolchain after an unrelated build does not prove that build's environment. Diagnostic mode permits a valid dirty-source or post-hoc manifest but remains `authoritative:false`. A diagnostic without a manifest is recorded as `legacy_unverified`; pre-v1 manifests and old measurement evidence are also `legacy_unverified` and can never be release-ready.

New evidence uses `wikijump.targeted_corpus_render_regressions.v2` or `wikijump.full_corpus_render_inventory.v2`. Its `candidate_manifest.binding` object records the artifact key, manifest digest, verification status, and release readiness. The acceptance ledger independently requires the canonical targeted scope of 11 named fixtures with 10 observations each and the canonical full scope of exactly 24,430 items. The old v1 schemas remain readable historical evidence but do not prove an artifact binding.
